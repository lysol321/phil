# Ground Truth + Backlog Mapping

## Ground-truth check — mandatory, not skippable

Check the target's own canonical status doc if it has one (e.g. `tasks/NEXT.md`-style entry point), `git log`, and current test/build state. Never act on a wiki page, a memory entry, or a design doc alone until it's verified against something live. State what was checked and when.

As part of this check, confirm the target is actually a git repo with write access and can hold a `tmp/` dir (`mkdir -p tmp` before the first `tmp/` write — the dir is not tracked and won't exist on a fresh clone) — Blocks require both (see `blocks.md` → Git Convention). If it isn't a git repo, or there's no write access, stop and report that rather than attempting to set up a Block — the Block system assumes both and has no fallback.

## Campaign check — resume the outer loop

If `tmp/campaign-{project}.md` exists in the target, this activation is a campaign **TICK**, not a fresh start. Verify the campaign's `campaign_stop` predicate against live state first — if it is already met AND no `closed:` field exists, write `closed: <ISO UTC from date -u>` with one-line evidence of the met predicate, remove the campaign file's absolute path from `<phil-repo>/tmp/watchdog-registry.md` (cron mode only — see `blocks.md` → Execution-mode status), report done, and stop rather than working. If `closed:` field already present, report and stop. Otherwise, this is a tick: re-run ground-truth delta check, delta-update the mapping, rebuild the roster, and drive per the Campaign Loop. On each tick, append a tick record to the campaign file (date, delta summary, blocks advanced/completed/authored, queue actions taken, cost line, next-tick intent) — see `blocks.md` → Campaign File Schema and `loops-core.md` → Campaign Loop.

No campaign file exists: if the user asks for ongoing/autopilot-style work ("put X on autopilot", "drive X to <goal>"), offer to open one. Never invent a campaign file or `campaign_stop` silently — deriving one requires naming the source (e.g. the canonical status doc's milestone list, an owner-named goal). If the user provides a campaign name and target Stop, create the file; then, in cron mode only (see `blocks.md` → Execution-mode status), append the campaign file's absolute path to `<phil-repo>/tmp/watchdog-registry.md` so the Watchdog can monitor it (campaign files are listed alongside Block state paths in the registry). Otherwise ask for both before proceeding (2026-07-17).

**STALE markers age out — verify the thing they point at, not just trust the pointer.** A `blocks.md` Block marked STALE often ends with a sentence like "the real next Block is derived from `tasks/NEXT.md` (X is the current claimable-now candidate), not this." That sentence was authored in a previous session and can itself be stale: by the time you read it, the canonical status doc's claim about X may have drifted. Concrete failure mode (2026-07-14): the STALE `core-loop-gate` Block's footnote named "T2SIM-02..07 is the current claimable-now candidate." When ground-truth ran, CHANGELOG and the repo state showed T2SIM-02..07 had been *shipped as GAP stubs* the previous week — the STALE marker's pointer was itself stale. The lesson: when a STALE marker names a candidate, grep the actual repo + read the canonical status doc fresh + spot-check the CHANGELOG, don't just trust the footnote. The same failure mode applies to any "see X for next steps" hand-off — verify X is current, not that the hand-off reference looks plausible.

## Map the backlog to Loop/Block shape

Pull every open item off the canonical status doc — no status doc? Fall back to `git log`, open issues, and the repo's own tasks dir, or ask the user. Not just the loosest thread lying around: an uncommitted file in `git status` is a candidate to weigh, not an automatic pick.

For each item: which linked Loop template matches its Goal/Stop shape (User Test, Calibration/Tuning, Fix Bugs From a Log, etc.), and which Product Pipeline phase it sits in (Build/Validate/Harden/...). Two templates both plausibly fit? Pick the closer Stop-condition match, note the alternative.

Human-gated items still map — and they're claimable: mark the gate, run it under the Emulated-gates protocol (`blocks.md` — provisional verdict + heads-up, proceed). Only items hitting the narrow bar (`blocks.md` → "Default posture: autonomous"; major design shift only) or a genuine canon contradiction map as hard-blocked, not claimable. Ordinary taste calls — is it fun, does it feel right, is this good enough — are the agent's to decide and log, not defer; don't flag those here just because a human *could* weigh in. If *everything* mapped turns out hard-blocked under that narrow bar, report that and stop rather than inventing agent-claimable work.

Present the *whole* mapping before proposing what to run next, and justify the pick against it (why this item, why now, not just why it's pickable) — a mapping that silently omits open items is invalid. The mapping's ranking is what feeds the roster pick (top 2-3 path-disjoint claimables — see `blocks.md` → Roster), so rank it, don't just list it.

## Spec-driven trigger — thin backlog, rich spec

The mapping above is *pull-based*: it maps a backlog that already exists. When the target instead has a rich design/spec doc but a thin or empty enumerated backlog — a feature specced but not yet broken into tasks, a spec that outran its status doc — do **not** report "nothing claimable" and stop. That empty-backlog-plus-live-spec state is itself the signal to go proactive: run the **Spec Decomposition Loop** (`loops-core.md`) inside a **`spec-conformance` Block** (`blocks.md`), which decomposes the spec into a requirement ledger (every normative clause → a claimable item with a testable Stop + live current-state). The decomposition ledger then *is* the enumerated backlog this mapping step consumes normally — map and drive the `unmet`/`partial` clauses like any other backlog.

**Guardrail — the trigger needs a concrete owner-intent signal before it fires.** A spec can't be verified against live state the way a status doc can (it describes the not-yet-built), and the per-clause current-state check only proves what the code *does*, not that the owner wants the spec *built*. So an empty backlog next to a large design doc is NOT automatically a decompose signal — that's exactly the "stop designing, start playing / freeze docs until the slice proves fun" premature state phil's own records flag (see the archived `core-loop-gate` instance). Require at least one of: (a) the canonical status doc references the spec as active/current work, (b) the spec is git-recent and not marked draft/aspirational/future, or (c) the owner named the spec in the activation ("phil on X, conform to spec Y"). None of those present → treat it as a design doc to distrust, report the thin backlog honestly, and do not invent conformance work. This keeps the proactive path from manufacturing a backlog out of an aspirational doc.

## Authority direction — spec-driven Blocks invert doc-suspicion

The ground-truth rule at the top of this file ("never act on a design doc alone until verified against live state") assumes code is the source of truth and a doc is suspect. That is correct for backlog-driven work, and stays the default. A Block carrying `authority: spec` (state-file field, `blocks.md` → State File Schema) inverts this *for its own scope*: the spec is the conformance target, so a clause the code doesn't yet satisfy is a work item, not a doc-drift finding to reconcile backward. What does **not** change: the live current-state check still runs per clause (does the code already meet it? — that's ground truth, unchanged). What flips is only the *fix direction* when the two disagree — under `authority: spec`, unmet → build toward the spec; under `authority: code` (default), drift → doc follows code (Design Doc Alignment). A spec-authoritative Block never skips ground truth; it only chooses which side gives. Whole-system posture stays code-authoritative — spec-authority is per-Block, opt-in, never global.

Persisting it: persist the mapping to `tmp/mapping-{project}.md` in the target repo; on a later run, if that file already exists, verify it against ground truth and delta-update rather than rebuilding from scratch — same rule as the index's "ledger exists → resume, don't restart" contract.
