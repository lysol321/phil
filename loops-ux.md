# UX and Validation Loops

User-facing validation: deterministic interaction sweeps first, simulated-user judgment second, human hands-on last - the cheapest rung that can catch a finding wins (rung attribution, Triage Loop in [`loops-core.md`](loops-core.md)). Same Goal/Checkpoint/Stop/Track/Extras contract as [`loops.md`](loops.md) -> Loop contract.

## UI Design Loop
Goal: Design the UI. Continue until happy with the architecture.
Checkpoint: After each significant step: visually test the system, run autoreview, commit.
Stop: If 3 straight passes change nothing you'd defend, stop and report open design questions.
Track: tmp/uidesign-{project}.md

## Visual Inspection Loop
Goal: Open running app; capture actual rendered UI as screenshots for every major screen/state (empty, loading, full, error, hover, focus, mobile width, dark mode). View each image directly. Per screenshot, note what looks wrong: spacing, alignment, contrast, hierarchy, overflow, jank, AI-generated tells. Fix worst offender, reload, re-screenshot affected screen, confirm fix by eye.
Checkpoint: After each significant fix: run autoreview, then commit.
Stop: A full visual sweep surfaces nothing you'd change — list anything deferred.
Track: tmp/visual-{project}.md
Extras: Evidence is pixels, not DOM snapshots — actually open the screenshot; Playwright proves it works, this judges how it looks. For browser apps: `preview_start` → `preview_screenshot` is the judge; `preview_resize` for responsive + dark mode; canvas content needs a real screenshot (a DOM snapshot can't see canvas pixels).

## User Test
Goal: Exercise the product hands-on for coverage.
Checkpoint: After each significant step: note things liked, things disliked, log both.
Stop: A session adds nothing new to the like/dislike log; then summarize coverage gaps.
Track: tmp/usertest-{project}.md
Extras: Optionally preceded by Simulated User Pass (below) — a cheap agent pre-filter that catches friction before spending the human's time. Simulated User Pass never substitutes for this loop's gate verdict (which runs provisionally per Emulated gates — human ratifies async); it only reduces how much needs fixing before the gate runs. Scribe protocol: when the human drives the product — ratifying a gate or free-form — a scribe agent runs alongside in chat or ledger channel, converting every friction utterance into a typed punch item (`fix | tune | design | taste`) with timestamp + journey-beat context, sampling "how does it feel right now, 1-5" passively (inferring feel from utterances at natural pauses, explicit 1-5 ask only when activity pauses, never interrupting). Wall-clock timestamps recorded at major progression beats. The human verdict stays verbatim (existing convention) — the scribe output feeds Triage. Rationale: a human gate verdict of "needs polish" with no itemized list spends the scarcest resource in the pipeline (owner hands-on minutes) for ~1 bit of information (2026-07-16).

## Mechanical Sweep Loop
Goal: Drive the real running app with Playwright (no LLM judgment, no screenshots, no vision) and assert DOM/event-state invariants that don't need eyes to check: focus ownership after every panel/modal/button interaction returns to the right element (never silently trapped), keyboard input isn't swallowed after a mouse click anywhere in the UI, toggle controls agree with their own state regardless of which input method drove them (mouse vs keyboard), tab order on any dialog/overwrite-prompt reaches every actionable button, commands issued while paused/blocked queue and drain exactly once (no double-fire, no drop). Author these as ordinary Playwright specs (e.g. `e2e/specs/mechanical-sweep.spec.ts`) — one `test()` per invariant, not one giant scripted playthrough.
Checkpoint: After each invariant gets a passing assertion: commit. After any invariant catches a real bug: fix root cause, add the assertion as permanent regression coverage (it stays in the suite after the bug's fixed — that's the point), commit.
Stop: Full suite green, zero new invariant violations found this run.
Track: tmp/mechsweep-{project}.md
Extras: **Ground-truth loop, not taste** — a violation here is objectively true/false, unlike Simulated User Pass's UX-bar judgment calls. Existed because roughly 5 of 7 Simulated User Pass findings on one project (focus traps, one-way toggle buttons, lost keyboard focus after a click, paused-input queue burst, dialog tab-order landmines) were DOM/event-state bugs a scripted assertion catches deterministically and far cheaper than an LLM roleplaying a persona and eyeballing screenshots — this loop exists to front-load exactly that class of bug so the expensive judgment-based loops downstream spend their budget on things only judgment can catch. Does NOT replace Simulated User Pass or User Test (visual/taste findings — layout, "does this feel right," an inverted label a script can't know is wrong — still need those); does not replace a project's own headless-core state-hash oracle either, if it has one (that catches simulation-logic drift, this catches DOM/interaction-layer bugs — different layer, same "cheap deterministic pre-filter before an expensive judgment pass" shape). If the project's e2e visual-user test skill has a standing Core-Invariant ban on Playwright as a substitute for visual inspection (see e.g. a project's own `e2e/user test/SKILL.md`), that ban is about *evaluating a scenario's pass/fail*, not about *this loop* — this loop never renders a verdict on look-and-feel, only on mechanical state correctness, so it doesn't violate that boundary.

## Simulated User Pass
Goal: Roleplay a first-time user against the build to catch friction before it burns the real human's time. Not the building agent grading its own work — use a frontier-tier model (per `models.md`) via the runtime's delegate capability (`PORTABILITY.md` → Runtime adapters; no delegate capability → run the persona in a manually opened fresh session), explicitly instructed to play a named persona, not to review code. Two modes: **(a) free-roam friction hunt** — the persona plays freely, logging every UX-bar violation and dead-click; **(b) archetype beat-walk scorecard** — step the persona through the project's enumerated progression (journey map, milestone table, onboarding funnel) beat by beat, scoring each. Use (b) whenever the project HAS such a progression — a committed artifact enumerating discrete stages (e.g. a journey map, `data/beats.json`, a milestone table, a design-doc progression section); it turns the pass into a comparable regression benchmark instead of a one-off friction list. Fall back to (a) when no such artifact exists (ask the caller if unclear). Pick 1–3 archetypes per run from a stated set (e.g. impatient power user, confused newcomer, tutorial-skipper, methodical explorer) — confirm the set with the caller or infer it from the product's design docs and name the source in the ledger; the archetype's behavior IS the test: a tutorial-skipper exposes onboarding holes a patient user never reaches. **Boundary with Onboarding / First-Session Loop:** if the progression is onboarding-only (no mid-journey/late-journey stages), the Onboarding Loop (fixed task list + time-to-first-success metric) is the gate; beat-walk covers mid-journey-and-beyond progression, or runs earlier as a cheap pre-filter for onboarding without substituting for that gate.
Checkpoint: After each session: log every UX-bar violation plus any dead-click/unclear-affordance friction, with repro steps, and apply **rung attribution** (defined in Triage Loop's Checkpoint above) — tag each finding with the cheapest rung that could have caught it; a finding cheaper than this loop's own (roleplay) auto-spawns a coverage task at that rung, typically a new Mechanical Sweep invariant. Commit. In **beat-walk mode** the log IS a scorecard — one row per beat: `time · beat (id/dev-or-stage) · goal (what the user THINKS they're doing) · information state (what they ACTUALLY know at this point) · friction 0–5 · motivation 0–5 · clarity 0–5 · one line of evidence citing the specific design element responsible (beat id, authored line, UI element, feature)`. Ground every row in a real artifact read from the repo (the actual journey map, content bank, rendered UI) and state what was read — never a remembered or invented beat. Preflight (below) confirms a frontier-tier model and a foregrounded tab; if the walk includes onboarding beats, start from a clean profile. If the archetype never reaches a beat (a progression wall — a resource/gate bottleneck stalls advancement), still record the row marked `reached: false` with the blocker named in the evidence column, rather than omitting it or inventing scores — an unreached beat is itself a finding (often the loudest one).
Stop: A full pass surfaces no new (vs the most recent prior scorecard in the Track ledger) UX-bar violation and no new friction note; in beat-walk mode, the two standing findings (Extras) are also derived and recorded. Then hand off to User Test (its gate runs provisionally per Emulated gates, human ratifies async). Give-up bound: 3 straight passes with nothing new.
Track: tmp/simuser-{project}.md — append each run's scorecard rather than overwriting, so the same archetype+beats re-scored on a later build is a UX regression signal (same rationale as Onboarding Loop's fixed task list).
Extras: UX bar (measurable proxy, not vibes): reaching something useful or fun from a decision point should take **at most 3 clicks/keypresses and 5 seconds**. A violation is a finding, not a taste call — log it even if the roleplaying agent personally didn't mind it. **Two standing findings from every beat-walk, both routed to Triage:** (1) the **3 lowest-scoring beats** by composite `motivation + clarity + (5 − friction)`, lower = worse (on a tie at the cut, include all tied beats — a run may report more than 3); (2) the **longest contiguous stretch with no meaningful reward or decision** — no beat fire, resource gain, unlock, or real choice — reported as both a beat span and a wall-clock span and as a % of the session (e.g. "beats 11→14, ~28 min, 45% of the session"), because an impatient user reads a long value-less stretch as abandonment, not "keep going." An `reached: false` wall row terminates the stretch measurement — the wall IS the end of meaningful progression, so the stretch runs from the last reward to it. Model choice matters more than usual here: a small/cheap model roleplays a user badly (too patient, too literal) and the pass is worthless. Optionally preceded by Mechanical Sweep Loop (above) — a cheaper, non-LLM pre-filter for the DOM/event-state bug class; when both run in a Block, Mechanical Sweep goes first so this loop's (expensive) budget isn't spent re-discovering what a script could've caught. **Environment preflight (2026-07-16 — promoted from a project ledger note after 2 of 3 passes on one Block came back environment-tainted, producing false-positive findings and wasted triage):** before driving any beat, verify the target tab is actually foregrounded and rendering — `document.visibilityState === "visible"`, `document.hasFocus() === true`, and that the render loop (`requestAnimationFrame` or equivalent) is ticking at a real frame rate, not starved. Mute audio if the app has sound. A backgrounded/unfocused tab silently starves rendering and input timing, producing findings that look real but aren't — fix the tab state first, don't run the pass and triage the noise afterward.

## Polish / Feel Loop
Goal: Iterate interaction feel (micro-animations, transitions, haptics, sound cues) on a specific interaction list.
Checkpoint: After each pass: capture before/after clip (video + waveform), commit.
Stop: Every interaction on the list has a captured clip and passes a heuristic check (animation/cue actually fires, timing lands within the spec band, no zero-duration transition, no missing cue) — proceed on that, don't wait for a human to watch the clips. If a reference target is supplied, prefer matching it (transition durations, cue-to-action latency) over the heuristic.
Track: tmp/polish-{project}.md
Extras: Agents can't perceive feel directly, so the heuristic is a proxy, not a felt judgment — log every clip path so a human can spot-check later, but that check is optional and non-blocking. Escalate to a human mid-loop only if the pattern suggests the interaction itself needs redesigning, not for "does this specific tweak feel right."

## Onboarding / First-Session Loop
Goal: Test the first-session experience from a clean profile through the first meaningful success, using a novice persona and a fixed task list.
Checkpoint: Record time-to-first-success, dead ends, unexplained terms, missed affordances, unnecessary steps, and whether the user understands the next goal.
Stop: Every first-session scenario reaches its intended milestone within the defined time/click budget with no unexplained blocker or mandatory intervention.
Track: tmp/onboarding-{project}.md
Extras: Distinct from Simulated User Pass: this loop is specifically about new-user comprehension and activation, not general UX friction. Run from a clean profile and preserve the exact task list so later builds are comparable.
